# แผนนำเสนอระบบต่อคณะกรรมการ

เป้าหมายของการนำเสนอ: ให้กรรมการเห็นว่า (1) ระบบแก้ปัญหาจริงของงานคัดเลือกนักกีฬา (2) กฎและสิทธิ์ถูกบังคับที่ฝั่งเซิร์ฟเวอร์จริง ไม่ใช่หน้าจอสวย ๆ (3) โมดูล "สู่ความเป็นเลิศ" ต่อยอดจากข้อมูลที่ระบบมีอยู่แล้ว ไม่ใช่ระบบแยก

## โครงเวลา 20 นาที (สาธิต 12–14 นาที + ถาม-ตอบ)

| เวลา | หัวข้อ | สิ่งที่ต้องให้เห็นบนจอ |
|---|---|---|
| 0–2 นาที | ปัญหาและขอบเขต | สไลด์เดียว: ขั้นตอนเดิมทำด้วยกระดาษ/Excel → ปัญหาคือคุณสมบัติตกหล่น เอกสารกระจาย ตรวจย้อนหลังไม่ได้ |
| 2–4 นาที | ภาพรวมบทบาท | สไลด์ไดอะแกรม 5 บทบาท + ลำดับอนุมัติ ชมรม → เจ้าหน้าที่ → ประกาศผล → นักกีฬายืนยันสิทธิ์ |
| 4–8 นาที | สาธิตเส้นทางหลัก | นักกีฬาสมัคร → ชมรมจัดบัญชีตัวจริง/สำรอง → เจ้าหน้าที่ตรวจหลักฐาน → ประกาศผล |
| 8–13 นาที | สาธิต "สู่ความเป็นเลิศ" | ตาม `docs/EXCELLENCE_DEMO_SCRIPT.md` (โหมดสาธิต) |
| 13–15 นาที | ความถูกต้องและความปลอดภัย | สิทธิ์ฝั่งเซิร์ฟเวอร์, การกันบันทึกซ้ำ, optimistic lock, ชุดทดสอบ |
| 15–20 นาที | ถาม-ตอบ | — |

ถ้ามีเวลาแค่ 10 นาที ให้ตัดช่วง 4–8 เหลือเฉพาะ "เจ้าหน้าที่ตรวจหลักฐาน → ประกาศผล" และตัด 13–15 ไปตอบในคำถาม

## ลำดับการกดจริง

### ช่วงเส้นทางหลัก (บัญชี STAFF)

> **ข้อมูลตัวอย่างสร้างไว้แล้ว** (19 ต.ค. 2569) เดิมฐานข้อมูลไม่มีใบสมัครเลยและไม่มีกีฬากรีฑาในรายการแข่งขัน จึงเพิ่มโควตากรีฑา ชมรมกรีฑา บัญชีรายชื่อที่ชมรมส่งแล้ว และใบสมัคร 3 ราย พร้อมเอกสารแนบ 4 ไฟล์ต่อคน · วิธีสร้างใหม่หรือลบทิ้งอยู่ใน [scripts/demo-applications/README.md](../scripts/demo-applications/README.md) · ถ้าตอนซ้อมกดอนุมัติหรือประกาศผลไปแล้ว ให้รัน seed ใหม่เพื่อคืนสถานะตั้งต้นก่อนนำเสนอจริง

1. `/staff/applications` — ชี้ว่าเหตุผลที่ไม่ผ่านคุณสมบัติ (GPAX < 2.00 / อายุเกิน 28 / เข้าร่วมเกิน 5 ครั้ง) ระบบคำนวณให้เอง เจ้าหน้าที่ไม่ต้องไล่เช็กเอง
   - กรองกีฬาเป็น "กรีฑา" จะเห็น 3 ใบ: นายเกียรติศักดิ์ (กองกิจฯ อนุมัติ), นางสาวจิรารัตน์ (รอการพิจารณา), นายธีรภัทร (ชมรมอนุมัติ / รอกองกิจฯ)
2. กด "รายละเอียด" ของชมรมกรีฑา แล้วคลิกชื่อนักกีฬา — หน้านี้คือหัวใจของช่วงนี้ เพราะขึ้นเกณฑ์ทั้ง 3 ข้อเรียงให้เห็น (GPAX / จำนวนครั้งที่เข้าร่วม / อายุตามปีมหกรรม), รายการตรวจหลักฐาน 4 หัวข้อ, ประวัติการพิจารณา และเอกสารแนบ
   - เทียบนางสาวจิรารัตน์ (GPAX 1.85) ที่ขึ้น "เสี่ยงผิดระเบียบ กกมท. · เกณฑ์ 1: GPAX 1.85 (ตกเกณฑ์)" กับนายเกียรติศักดิ์ (3.20) ที่ขึ้น "✓ ผ่านเกณฑ์ กกมท. ครบ 3 ด้าน"
3. กด "เปิดเอกสาร" 1 ไฟล์ — ชี้ว่าไฟล์เป็น private ไม่ได้เปิดเป็น URL สาธารณะ ระบบออก signed URL อายุ 60 วินาทีให้หลังตรวจสิทธิ์ทุกครั้ง
4. `/staff/selection` — มีนายเกียรติศักดิ์ 1 คนพร้อมประกาศผล ชี้ว่าการประกาศผลเป็นการกระทำที่ย้อนกลับไม่ได้ และมีเงื่อนไขปิดประตู (หลักฐานครบ) ก่อนประกาศ · **อย่ากดประกาศจริงตอนสาธิต** ถ้าจะกด ให้ seed ใหม่หลังจบ
5. (ถ้ากรรมการอยากเห็นฝั่งผู้ใช้) เปิดแท็บบัญชีนักกีฬาที่เตรียมไว้ล่วงหน้า ให้เห็นสถานะและการยืนยันสิทธิ์ — รหัสผ่านของ 3 บัญชีอยู่ใน `scripts/demo-applications/accounts.local.txt` (ทุกบัญชีถูกบังคับเปลี่ยนรหัสผ่านครั้งแรก ให้เปลี่ยนให้เรียบร้อยก่อนวันนำเสนอ)

### ช่วงสู่ความเป็นเลิศ (ใช้ข้อมูลจริง ไม่ต้องเปิด `?demo=true`)

> ตอนนี้มีข้อมูลจริงของนักกีฬา 4 คนในระบบแล้ว (ดู [scripts/demo-applications/README.md](../scripts/demo-applications/README.md)) **แนะนำให้สาธิตด้วยข้อมูลจริง** เพราะไม่มีแถบ "ข้อมูลสาธิต" คาหน้าจอ ปุ่มบันทึก/แก้ไข/ลบใช้งานได้จริง และเชื่อมกับใบสมัครชุดเดียวกับช่วงก่อนหน้า · โหมดสาธิต (12 คน) ยังใช้ได้ถ้าต้องการตัวอย่างที่หลากหลายกว่า ชื่อนักกีฬาในสคริปต์เดิมเป็นชุดของโหมดสาธิต
>
> จุดที่ควรพูดเมื่อใช้ข้อมูลจริง: รายงานมีนักกีฬา 4 คน ไม่ใช่ 6 คน เพราะระบบนับเฉพาะใบสมัครที่กองกิจฯ อนุมัติแล้ว คนที่ตก GPAX และคนที่ยังรอพิจารณาไม่ถูกนับ — เป็นกฎเดียวกับที่เห็นในช่วงใบสมัคร

ลำดับที่เหมาะกับกรรมการ (ชื่อตามข้อมูลจริง):
1. **ภาพรวมนักกีฬา** `/staff/excellence` — ตัวเลขสรุป 5 ค่า แล้วชี้ "ต้องติดตาม" ที่มีครบทั้ง 4 แบบ
2. **แผนที่จุดอ่อนทีม** `/staff/excellence/heatmap` — 4 คน × 11 สถานี ระดับทุกช่องคำนวณจากตัวเลขดิบตามเกณฑ์กลุ่ม 9 ของเพศนั้น
3. **รายคน** นายเกียรติศักดิ์ แสนสุข (69900001) — จุดอ่อน 2 สถานี → แผน 2 ข้อผูกกับสถานีนั้น → ทดสอบซ้ำ 11.34 → 11.18 (−0.16s เกินช่วงคลาดเคลื่อน ±0.1s) จึง "ดีขึ้น" → กราฟพัฒนาการและไทม์ไลน์
4. **รายการลาน** นายชนาธิป ก้องเกียรติ — กระโดดไกล 7.12 ม. เทียบเป้า 7.20 ม. วัดเป็นเมตร ยิ่งไกลยิ่งดี และแผนเลยกำหนดแล้วแต่ยังไม่ทดสอบซ้ำ
5. **พิมพ์รายงาน** กด Ctrl+P ที่หน้าภาพรวม

ข้อมูลจริงชุดนี้ยังไม่มีกรณี "เปลี่ยนน้อยกว่าช่วงคลาดเคลื่อน" ซึ่งเป็นจุดขายทางวิชาการ ถ้ากรรมการถามเรื่อง SWC ให้อธิบายด้วยตัวเลขของนายเกียรติศักดิ์ (−0.16s เทียบช่วง ±0.1s จึงนับว่าดีขึ้น ถ้าเปลี่ยนแค่ 0.04s ระบบจะบอกว่า "ไม่เปลี่ยนชัดเจน") หรือสลับไปโหมดสาธิตเพื่อเปิดกรณีของนางสาวพิมพ์ชนก

ถ้าจะสาธิตด้วยโหมดสาธิตแทน ให้ใช้ลำดับนี้จาก `docs/EXCELLENCE_DEMO_SCRIPT.md`:
1. **ภาพรวมนักกีฬา** `/staff/excellence` (ชื่อเมนูในระบบคือ "ภาพรวมนักกีฬา") — ตัวเลขสรุป 5 ค่า + รายการที่ต้องสนใจ (ยังไม่ตั้งเป้า / ยังไม่มีผล / อ่อนแต่ไม่มีแผน / แผนเลยกำหนด) นี่คือหน้าที่ผู้บริหารเปิดดูหน้าเดียวจบ
2. **แผนที่จุดอ่อนทีม** `/staff/excellence/heatmap` — บอกว่าทั้งทีมอ่อนเรื่องอะไรมากที่สุด ใช้ตัดสินใจเรื่องโปรแกรมฝึกรวม
3. **รายคน** นายภานุวัฒน์ ศรีสุข — จุดอ่อนตามเกณฑ์กลุ่ม 9 → แผนผูกกับจุดอ่อน → ทดสอบซ้ำ → ผลแข่งดีขึ้นเกินช่วงคลาดเคลื่อน
4. **จุดขายทางวิชาการ** นางสาวพิมพ์ชนก — เวลาดีขึ้น 0.04 วินาที ระบบ **ไม่** บอกว่าดีขึ้น เพราะอยู่ในช่วงคลาดเคลื่อนของการจับเวลา (SWC) ประโยคที่ควรพูด: "ระบบออกแบบให้ไม่ตีความข้อมูลเกินกว่าที่ข้อมูลรองรับ"
5. **พิมพ์รายงาน** กด Ctrl+P ที่หน้าภาพรวม ให้เห็นว่าออกเป็น A4 แนวนอน เมนูและปุ่มหายไป และพิมพ์ครบทุกแถวไม่ใช่แค่หน้าแรก — ตอบโจทย์ "เอาไปแนบรายงานประชุมได้เลย"

## ประโยคสำคัญที่ควรพูด (และที่ห้ามพูด)

ควรพูด:
- "เกณฑ์สมรรถภาพใช้เกณฑ์กลุ่ม 9 ตามเอกสารจริง ไม่ได้ตั้งเกณฑ์เอง 11 รายการทดสอบ 5 ระดับ"
- "เป้าหมายรายการแข่งเจ้าหน้าที่เป็นผู้กำหนดเอง ระบบไม่เดาค่าแทน ถ้ายังไม่ตั้งจะขึ้นว่า 'ยังไม่ตั้งเป้า' ชัดเจน"
- "ข้อมูลสาธิตแยกจากข้อมูลจริงและแก้ไขไม่ได้ มีแถบกำกับทุกหน้า"
- "การเปลี่ยนแปลงหลังแผนเป็นการ *ติดตามผล* ไม่ได้พิสูจน์ว่าเกิดจากแผนฝึกเพียงอย่างเดียว"

ห้ามพูด (เกินกว่าที่ระบบทำจริง):
- อย่าบอกว่าระบบ "ทำนาย" ผลการแข่งขัน — ระบบเทียบกับเป้าที่คนตั้งเท่านั้น
- อย่าบอกว่ารองรับหลายกีฬาแล้ว — โครงหน้าเตรียมไว้ให้ขยายได้ แต่ตอนนี้มีกรีฑาชนิดเดียว
- อย่าบอกว่าผ่าน WCAG เต็มรูปแบบ — บอกว่าตรวจด้วย axe แล้วไม่พบ violation แต่ยังไม่ได้ทดสอบกับโปรแกรมอ่านหน้าจอจริง

## คำถามที่กรรมการน่าจะถาม

| คำถาม | คำตอบสั้น |
|---|---|
| ข้อมูลที่โชว์เป็นข้อมูลจริงหรือ | เป็นข้อมูลสาธิต (ระบุไว้บนหน้าจอ) โครงสร้างและกฎเหมือนของจริงทุกอย่าง ข้อมูลจริงยังอยู่ระหว่างนำเข้า |
| ถ้าเจ้าหน้าที่สองคนแก้พร้อมกัน | ใช้ optimistic lock ด้วยเลข revision ถ้าชนกันระบบตอบ 409 และให้โหลดใหม่ ไม่เขียนทับเงียบ ๆ |
| กันการบันทึกผลซ้ำอย่างไร | ตรวจที่เซิร์ฟเวอร์ว่ามีผลของนักกีฬาคนนั้น รายการนั้น วันนั้นอยู่แล้วหรือไม่ ถ้ามีจะปฏิเสธ (409) |
| นักกีฬา/โค้ชเข้าดูได้ไหม | **ยังไม่ได้** ตอนนี้จำกัดเจ้าหน้าที่และผู้ดูแล เป็นงานเฟสถัดไปที่ต้องออกแบบสิทธิ์ก่อน — ตอบตรง ๆ อย่าเลี่ยง |
| ทำไมเลือกกรีฑาอย่างเดียว | เพราะหน่วยวัดชัดเจน (เวลา/ระยะ) ทำให้เทียบกับเป้าได้ตรงไปตรงมา และใช้พิสูจน์โครงก่อนขยายกีฬาอื่น |
| วัดความสำเร็จอย่างไร | เวลาที่ใช้ตรวจใบสมัครต่อราย, จำนวนนักกีฬาที่มีเป้าและแผนครบ, จำนวนที่ดีขึ้นเกินช่วงคลาดเคลื่อน |
| เทียบ 100 ม. กับ 400 ม. ได้อย่างไร | ใช้ "% ของเป้า" ไม่ได้ใช้ตารางคะแนนสากล เพราะเป้าเป็นของมหาวิทยาลัยเอง |
| ความปลอดภัย | ตรวจสิทธิ์จาก JWT + ตรวจฐานข้อมูลซ้ำทุกคำขอ ไม่เชื่อค่าจากฝั่งเบราว์เซอร์ เอกสารเข้าถึงผ่าน API ที่ตรวจสิทธิ์เท่านั้น |

## บทพูดต่อหน้า และจุดที่ดูไม่เรียบร้อย (เดินจริงเมื่อ 19 ต.ค. 2569)

เดินครบทั้งลำดับด้วยบัญชีเจ้าหน้าที่บน `http://127.0.0.1:3000` ข้อมูลจริง ไม่ใช้โหมดสาธิต

### 1. `/staff/applications`
พูด: "หน้านี้คือโต๊ะทำงานจริงของเจ้าหน้าที่ ใบสมัคร 6 ใบ ระบบแยกให้แล้วว่าใบไหนรอชมรม ใบไหนรอกองกิจฯ และกรองตามกีฬา สถานะ หรือค้นชื่อได้ทันที ส่งออก CSV/XLSX ไปทำรายงานต่อได้"
- แถวเรียงจากใหม่ไปเก่า คนที่เป็นตัวเอกของเรื่อง (69900001) จึงอยู่ล่างสุด ให้เลื่อนลงไปหรือกรองก่อนพูด
- **ไม่เรียบร้อย:** การ์ดสรุปด้านบนไม่ครบความจริง — มี 6 ใบ แต่นับแค่ "รอชมรมพิจารณา 1" กับ "รอกองกิจการนิสิต 1" ส่วน "ผ่านการคัดเลือก" ขึ้น 0 ทั้งที่มี 4 ใบที่กองกิจฯ อนุมัติแล้ว (ช่องนั้นนับเฉพาะใบที่ประกาศผลแล้ว) ถ้ากรรมการถาม ให้ตอบว่า "ผ่านการคัดเลือก" หมายถึงประกาศผลอย่างเป็นทางการแล้ว ไม่ใช่อนุมัติแล้ว

### 2. หน้ารายละเอียดชมรมกรีฑา
พูด: "ทุกใบสมัครระบบขึ้นเกณฑ์ กกมท. ทั้ง 3 ข้อให้เห็นพร้อมกัน เจ้าหน้าที่ไม่ต้องเปิดเอกสารไล่คำนวณเอง" แล้วเทียบแถวนางสาวจิรารัตน์ (แถบแดง "เสี่ยงผิดระเบียบ กกมท." + "เกณฑ์ 1: GPAX 1.85 (ตกเกณฑ์)") กับแถวที่ขึ้น "✓ ผ่านเกณฑ์ กกมท. ครบ 3 ด้าน"
- **ไม่เรียบร้อย:** หัวหน้าขึ้น "ตัวจริง 0 คน · ตัวสำรอง 0 คน" และทุกชื่อมีป้าย "ยังไม่ได้ระบุ" ทั้งที่มี 6 คนในบัญชี เพราะหน้านี้รู้จักแค่ตัวจริง/ตัวสำรอง ส่วนกรีฑาเป็นกีฬาประเภทบุคคลที่ใช้สถานะ `selected` (`app/staff/applications/[clubId]/[competitionId]/page.tsx:106`) เป็นช่องว่างของ UI จริง ไม่ใช่เรื่องของข้อมูลตัวอย่าง — ถ้าจะแก้ก่อนนำเสนอคือเพิ่มคำว่า "ผ่านการคัดเลือก" ให้ `selected` และนับรวมในหัวเรื่อง
- ถ้าไม่แก้ ให้พูดนำไว้ก่อนว่า "กรีฑาเป็นกีฬาบุคคล จึงไม่มีตัวจริง/ตัวสำรอง"

### 3. เอกสารแนบ

- **ไม่เรียบร้อย:** เมื่อกด "เปิดเอกสาร" เบราว์เซอร์จะเด้งไปที่โดเมน `supabase.co` และไฟล์ที่เปิดคือ PDF เปล่าที่เขียนว่า "DEMO DOCUMENT - NOT A REAL RECORD" — เตรียมพูดล่วงหน้าทั้งสองเรื่อง หรือเปิดไฟล์ไว้ในแท็บแยกก่อนเริ่ม

### 4. `/staff/selection`
พูด: "นักกีฬา 4 คนที่ผ่านการอนุมัติแล้วพร้อมประกาศผล การประกาศผลเป็นการกระทำที่ย้อนกลับไม่ได้ ระบบจึงแยกหน้าออกมาและมีร่องรอยย้อนหลัง"
- **อันตราย:** ทั้ง 4 คนถูกติ๊กไว้ล่วงหน้า และปุ่ม "ประกาศผลและขึ้นทะเบียน (4 คน)" เป็นปุ่มน้ำเงินเด่นมุมขวา กดพลาดครั้งเดียวคือประกาศผลจริงทั้งชุด ให้กด "ยกเลิกการเลือกทั้งหมด" ก่อนเริ่มพูด
- **ไม่เรียบร้อย:** การ์ดเจ้าหน้าที่ทีมสองใบขึ้น 0 ท่าน เพราะยังไม่มีข้อมูลส่วนนั้น ให้พูดสั้น ๆ ว่าเป็นอีกเส้นทางที่ยังไม่ได้สาธิตวันนี้

พูด: "นี่คือหน้าที่ผู้บริหารเปิดดูหน้าเดียวจบ — ตัวเลขสรุป 5 ค่า แล้วตามด้วยรายการที่ต้องลงมือ" แล้วชี้ "ต้องติดตาม" ที่ครบทั้ง 4 แบบ

- **ไม่เรียบร้อย:** "พัฒนาขึ้นหลังทดสอบซ้ำ 100%" มาจากคนเดียว ให้พูดตัวส่วนออกมาเองว่า "1 จาก 1 คน ยังเป็นกลุ่มตัวอย่างเล็กมาก" ก่อนกรรมการจะทัก

### 9. การพิมพ์

### เรื่องที่กระทบทุกหน้า
1. **แถบเครื่องมือของ Next.js (วงกลมมุมซ้ายล่าง) ติดอยู่ทุกหน้า** เพราะรันด้วย `npm run dev` — ต้องรันด้วย production build (`npm run build` แล้ว `npm start`) ไม่งั้นกรรมการจะเห็นปุ่มนักพัฒนาตลอดการนำเสนอ นี่คือจุดที่เห็นชัดที่สุด
2. ความกว้างหน้าต่างสำคัญกว่าที่คิด: ต้องการอย่างน้อย ~1,280 px สำหรับหน้าแผนที่จุดอ่อนทีม ดูเช็กลิสต์เรื่องการซูมด้านบน
3. ปุ่มที่กดแล้วย้อนไม่ได้ (ประกาศผล, ลบผลแข่ง, ยกเลิกผลทดสอบซ้ำ) อยู่ในเส้นทางที่ต้องชี้จอพอดี ซ้อมตำแหน่งเมาส์ให้ชิน
